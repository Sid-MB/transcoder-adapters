## 1. Base-vs-adapter circuit-tracing comparison overlay (the headline deliverable)

A patched circuit-tracer frontend that, for each full-replacement attribution graph, tags every node as a **base GemmaScope feature** (hexagon ⬢), an **adapter feature** (circle ●), or a **reconstruction-error node** (triangle ▲, ranked by |influence|). Clicking a feature node shows **per-feature proportions** ("fires on X% of tokens" = activation_frequency; top tokens with "NN%" = token_specificity) and **activation examples collected on our chat+web data**. Full replacement `MLP(x) = T_base(x) + T_adapter(x) + Err` yields the real error nodes for free (no RelP).

**Viewer UI (applies to every served set in this doc).** Each graph carries a **floating overlay banner** in the top-left — `Base ⬢ N (M shown) · Adapter ● N (M shown) · Error ▲ N (M shown)` — where N is the as-built composition (at the build `node_threshold`) and M recounts **live** as you drag the pruning slider, so it tracks what's actually on screen. Multi-prompt sets also label **every dropdown entry** with its composition, e.g. `[agree] base-vs-adapter — <prompt> … [Base ⬢ N  Adapter ● N  Error ▲ N]`, so you can pick a prompt by how much adapter it recruits. These come from the shared frontend patch (`analysis/attribution/comparison_frontend.py`) and apply automatically on serve — no per-set work.

**Now points at the best data:** the headline demo is the full-corpus **`ms100000`** overlay (§6) — base/adapter examples drawn from the **entire lmsys val + matched fineweb** (`base_ms100000` + `adapter_ms100000` baked in). Serve it, then open http://localhost:8044 :

## 2. Agree-vs-diverge experiment (does circuit tracing work, and does the adapter behave as theorized)

14 prompts where base+instruct **agree** (factual recall — base does the work) and 14 where they **diverge** (behavioral: instruction-following, format obedience, persona, refusal, …), each traced into a combined full-replacement graph; node composition aggregated per bucket. The enriched set adds **assistant-prefix deep-token tracing** so behaviors are probed mid-response, not just at the first token. Headline result: tracing works (28/28 graphs), KL(instruct‖base) independently validates the agree/diverge split, and — unlike the original facts-only set — the adapter now fires on **content tokens** on diverge (interpretable instruction verbs: Explain / Reply / Respond / List / Summarize), with the content fraction jumping **0.09 → 0.34**, on top of a roughly constant chat-template "format floor".

Results table — [`experiments/base_vs_adapter_circuit_trace/aggregate_results.json`](../experiments/base_vs_adapter_circuit_trace/aggregate_results.json):

| metric | agree (n=14) | diverge (n=14) |
|---|---|---|
| base features | 1102.5 | 1220.9 |
| adapter features | 44.1 | 61.0 |
| adapter on template tokens | 40.1 | 39.4 |
| **adapter on content tokens** | **4.0** | **21.6** |
| error nodes | 32.0 (capped) | 32.0 (capped) |
| adapter fraction | 0.039 | 0.048 |
| **adapter content fraction** | **0.087** | **0.337** |
| KL(instruct‖base) | 1.10 | 10.14 |

Note: absolute counts use `--max_feature_nodes 4096` (≈4× the original run) and error is capped at `--max_error_nodes 32`, so absolute base/adapter/error totals are **not** comparable to the older facts-only table — the comparable signal is the **fractions** (especially `adapter content fraction`, which moves 0.09 → 0.34).

## 6. Full-corpus collections + the vectorized/sharded pipeline that made them feasible

The largest, most thorough feature collections: each covers the **entire lmsys val split (100k rows)** plus a matched **100k fineweb** sample (vs the 1k–20k of §4). On HF:
- Base GemmaScope — **[base_ms100000](https://huggingface.co/siddharthmb/2026.TA.features_gemma-2-2b_gemmascope_width_16k_average_l0_76_ms100000_ml1024_tk1_hf83e96d574d2)**

**Drop-in full-corpus comparison overlay** — the §1 headline demo, rebuilt with these full-corpus collections (`base_ms100000` as `/base_features`, `adapter_ms100000` as `/adapter_features`) baked into one combined graph. Built on jagupard (job 16038728) → `/nlp/scr/siddharth/transcoder-adapters/graph_combined_ms100000`; serve it, then open http://localhost:8044 :

```sh
uv run --extra viz python -m analysis.attribution.serve_comparison_graphs --graph_file_dir /nlp/scr/siddharth/transcoder-adapters/graph_combined_ms100000 --port 8044
```

Why this needed engineering: the base/GemmaScope collection is **CPU-bound on dense accumulation** — GemmaScope fires ~76 features per token per layer, i.e. ~2M (feature, token) activation events per 1024-token sequence, and the per-event top-k/histogram bookkeeping is single-threaded Python; the GPU forward is a small fraction of the time (GPU sat at ~4% on a B200). Two changes made the full-corpus base feasible:

1. **Vectorized accumulation** — [`analysis/features/collect_feature_activations.py`](../analysis/features/collect_feature_activations.py) (commits `dc19060` → `a98682c`): replaced the per-event Python loop in `FeatureCollector.accumulate_batch` with vectorized `bincount` counts, a **running per-feature heap-min candidate threshold** (kills the per-unique-feature Python loop), **survivor-only** top-k iteration, and **exact-top-cap** `token_counts` (replaces the approximate Space-Saving — a strict accuracy improvement). Byte-exact parity on all deterministic outputs, gated by [`tests/test_accumulate_vectorized_parity.py`](../tests/test_accumulate_vectorized_parity.py); measured **2.3×–9.8×** (rises toward ~10× as the top-k heaps fill and the candidate rate drops). Residual floor is `torch.nonzero` over the dense activation tensor + per-retained-example context fetch.
2. **Sharded job array** — [`run_on_gpu/run_collect_base_shard.sh`](../run_on_gpu/run_collect_base_shard.sh): `--num_shards`/`--shard_index` fan the dense accumulation across N **independent** jagupard GPUs (no contention; injects the shard index from `$SLURM_ARRAY_TASK_ID`), each pickling partial state; one dependent merge job recombines them exactly via `FeatureCollector.merge_from` and uploads. `base_ms100000` ran as an 8-shard array (job 16010005, ~5.5–8.5 h/shard, ~0.8–1.2 s/seq vs ~3–4 s/seq pre-vectorization) → merge+upload (job 16010006).

Per-shard throughput logged to wandb project **`transcoder-feature-collection`** (runs `base_ms100000_shard0…7`). Produced by[^fullcorpus].
